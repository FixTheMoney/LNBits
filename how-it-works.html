How It Works

A visual walkthrough of the full payment flow — from QR generation to sats delivery — and how the system prevents recipients from claiming more than once.

System Architecture

Three actors, one protocol — no intermediaries

🧑‍💻

You (The Sender)

You configure the drop: amount per recipient, number of rounds, and expiry time. Your LNbits wallet funds every withdrawal. You never share your private keys — only your LNbits Admin API key is used.

LNbits Admin Key This Browser
⚡

LNbits (Your Node)

Your LNbits instance manages the LNURL-withdraw links. It enforces the uses: 1 constraint at the protocol level — ensuring each link can only ever be redeemed once, regardless of how many times the QR is scanned.

LNURL-withdraw uses=1 enforcement
📱

Recipients

Each recipient scans the QR with any Lightning-compatible wallet (Phoenix, Breez, Wallet of Satoshi, etc.). Their wallet fetches the LNURL callback, constructs a payment invoice, and receives sats automatically.

Any LN Wallet LNURL-withdraw One-time only

How Double-Dipping is Prevented

Three independent layers working together — protocol, link, and session

🔐 Layer 1 — Protocol Level

The strongest protection. The LNURL-withdraw link is created with uses=1 and is_unique=true. This is enforced by LNbits at the server level.

  • When a wallet calls the callback URL, LNbits checks remaining uses atomically
  • If uses_left = 0, LNbits returns an error and refuses to pay
  • No amount of retrying can bypass this — the link is exhausted at the database level
  • Even if a second person scans the same QR photo, LNbits rejects it
LNURL spec Server-enforced
🔄 Layer 2 — One QR Per Round

Each round generates a completely new, unique LNURL link. The previous QR code stops working the moment it's been claimed.

  • The app immediately rotates to a new link after each claim
  • Old QR photos shared via messaging apps become invalid
  • Each new link has a unique cryptographic identifier from LNbits
  • Expired links are explicitly deleted via the API to prevent late claims
Per-round rotation Deletion on expiry
🏷️ Layer 3 — Recipient Fingerprinting

Each successful claim is logged with a pseudonymous recipient ID tied to the round and timestamp. The blocked list provides an audit trail.

  • A unique token is generated per claim: round + timestamp + entropy
  • All claimed IDs are shown in the Recipient Log table in real time
  • The blocked fingerprints panel gives you visibility into who claimed each round
  • Session data is persisted to the database for post-session review
Audit trail DB persistence
⏱️ Layer 4 — Expiry & Cleanup

QR codes expire after a configurable time window. Expired links are deleted via the API, not just ignored — preventing late redemptions.

  • Countdown timer is displayed publicly — recipients know time is limited
  • On expiry: DELETE /withdraw/api/v1/links/{id} is called immediately
  • A fresh link is created for the next attempt — the round count continues
  • Expiry events are logged separately from claims in the session log
Time-bound API deletion

LNURL-Withdraw Anatomy

What's inside the QR code and how the protocol enforces one-time use

The QR code encodes a bech32-encoded LNURL string. When scanned, the recipient's wallet decodes it to a URL and makes an HTTP request to your LNbits instance. The response is a JSON object specifying the withdraw parameters:

// Step 1: Wallet fetches the LNURL callback URL // GET https://legend.lnbits.com/withdraw/api/v1/lnurl/{unique_hash} // Step 2: LNbits responds with withdraw parameters { "tag": "withdrawRequest", "callback": "https://legend.lnbits.com/withdraw/api/v1/lnurl/cb/{hash}", "k1": "a3f9b2c1...", // Random challenge token "minWithdrawable": 1000000, // msats (= 1000 sats) "maxWithdrawable": 1000000, // msats (fixed amount) "defaultDescription": "QR Drop Round 3", "balanceCheck": "..." // Optional balance check URL } // Step 3: Wallet generates an invoice and submits it // GET callback?k1={k1}&pr={bolt11_invoice} // Step 4: LNbits validates k1, checks uses_left > 0, pays invoice // → sets uses_left = 0 atomically { "status": "OK" } // ← success { "status": "ERROR", "reason": "Link already used" } // ← on retry
tag
Identifies the type as a "withdrawRequest" — tells the wallet to present a receive UI, not a payment UI.
k1
Challenge token — a random value LNbits generates. Must be echoed back in the callback to prove the wallet fetched the correct link.
min/maxWithdrawable
Both set to the same value (e.g. 1,000,000 msats = 1000 sats) — forces the exact amount. The wallet cannot request more or less.
callback
The endpoint to POST the invoice to. This is your LNbits server — it validates the invoice and executes the Lightning payment.
uses=1
Stored in LNbits DB — not in the LNURL itself. LNbits checks this atomically before processing any callback, preventing race-condition exploits.
is_unique
Forces a unique hash per link so that even if two links have the same parameters, their LNURL strings are different and cannot be confused.
